# Account project selection and project management (0.28)

The authenticated user's last selected project is stored in user_workspace_preferences per user and workspace. It is not an account-owner-wide default for all members. POST /api/preferences/project validates workspace membership and project ownership; viewers can change their own navigation preference, while project editing still requires owner/admin. The session determines the user; request user IDs cannot change another user's preference. Foreign project IDs are rejected. Removed project selections cascade away and fall back to the workspace default.

State refreshes read the saved choice without re-sending the previous in-memory project header. User-scoped database notifications invalidate open sessions; visibility refresh and a 60-second fallback cover reconnects. Explicit project URLs override the saved default on that page and save on initial navigation, not on every refresh. Scoped API reads never change the preference. Workspace switching preserves other workspace preferences. Support navigation is ephemeral and does not write the customer's preference. Preference records are included in the user's data export and cascade with account removal. Legacy browser project cookies are ignored.

/projects now manages all workspace projects, with search, status filters, summary counts, open and edit actions. Editing a non-selected project does not switch the user's selection. /projects/<id> displays the project's stats, shared material controls, environment assignment and Git configuration. Pausing or archiving uses the existing revision check and execution policies; projects are not permanently deleted by this UI.

The project tab is labelled Project environments. Every environment remains assigned to exactly one project for agent/file isolation. Allowed execution locations are workspace settings, while slots and hosting-minute balances are account-wide. No change grants cross-project tool access.
